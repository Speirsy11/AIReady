# AI Adoption Readiness Kit — Sample Comparison Matrix

> Local review aid only. This is not approval to publish, push, contact anyone, inspect private systems, process customer/user data, deploy anything, spend money, change accounts/credentials, or create a paid offer.

Use this matrix to compare the fictional samples quickly before deciding whether the kit is clear enough for a later approval-gated next step.

## Cross-sample summary

| Fictional sample | Safe draft-only candidate | Primary blocked workflows | Why blocked | Review lesson |
| --- | --- | --- | --- | --- |
| Northstar Bookkeeping Studio | Internal SOP summaries | Customer transaction categorization; client email replies | Private financial/customer data and customer-facing communication | Financial/private data can make high-value workflows unsuitable without explicit approval. |
| Greenfield Plumbing Co. | Internal job checklist updates | Emergency message replies; route prediction from live calendar | Customer-impacting communication, live schedules, locations, and customer addresses | Operational urgency does not override human review or data boundaries. |
| Maple Lane Retail | Internal product training notes | Reorder recommendations; complaint replies from order history | Live inventory/sales data, cashflow impact, private order data, customer-facing commitments | Business-impacting decisions and order/customer data need separate approval even when measurable. |

## Pattern checklist

A candidate is usually safer for a first draft-only pilot when most are true:

- [ ] It uses fictional, public, or explicitly approved non-sensitive internal notes.
- [ ] A human reviews every output before use.
- [ ] The output is internal-facing rather than customer-facing.
- [ ] The workflow does not connect to accounts, credentials, production systems, or automations.
- [ ] The success measure can be reviewed manually with examples.
- [ ] Stopping the pilot has no customer, cashflow, safety, legal, financial, or operational impact.

A candidate should be marked `[blocked]` when any are true:

- [ ] It needs customer/user records, private financial data, order history, live schedules, location data, payment data, vendor contracts, credentials, or production system access.
- [ ] It sends or drafts customer-facing, public, legal, financial, health, security, emergency, or complaint communication from real cases.
- [ ] It changes pricing, inventory, routing, bookings, account settings, promotions, fulfilment, dispatch, or payment behavior.
- [ ] It relies on live integrations, scraping private systems, or background automation.
- [ ] It treats AI output as final rather than draft work reviewed by a human.

## Buyer-fit patterns

Good-fit fictional buyer signals:

- Has repeated internal documentation or review work.
- Can provide non-sensitive sample material.
- Accepts a draft-only pilot with manual review.
- Values a clear stop condition over fast automation.
- Wants help prioritizing safe use cases before implementation.

Poor-fit or later-fit signals:

- Wants immediate automation, deployment, or external communication.
- Needs private/customer/regulatory data to show any value.
- Wants AI to make operational or financial decisions directly.
- Cannot separate internal drafts from customer-facing actions.
- Treats approval gates as paperwork rather than safety controls.

## Recommended use

During review, pick one fictional sample that resembles the buyer pattern under discussion, then confirm:

1. the safe pilot does not require private data;
2. the blocked workflows are obvious and non-negotiable;
3. the measurable evidence can be collected manually;
4. the next step is exactly one approval-gated action, not a bundle of external actions.

If a reviewer cannot explain these four points in under two minutes, improve the kit locally before any external step.
